This reading finishes the corpus: the links between articles, the revision histories, the daily page views, the language links, and a second corpus of 75 authors built from a curated list. On a sheet of paper, hand write answers to the following.

  1. Charlotte Brontë's article links to Elizabeth Gaskell's, who wrote her biography, so say what a link like that is actually evidence of, given that a Wikipedia editor added it in the last twenty years.
  2. Say why the page views are fixed to the 2025 calendar year rather than the last 365 days.
  3. Name a question about Victorian novels that a daily count of readers of the Emily Brontë article cannot answer no matter how carefully it was collected.
  4. The second corpus's birth years, death years, and gender columns came from no API at all, so say what has to be written down about that table before anyone else can trust it.
  5. Explain what it means that an unmatched curated title would have failed "silently," and what the corpus would have looked like if nobody had checked.

Solutions

1. What a link from Charlotte Brontë's article to Elizabeth Gaskell's is evidence of.

The link is evidence that some editor, at some point in the last twenty years,
decided Gaskell was worth linking from Brontë's article. It is a record of
present-day editorial judgment about the two women. It is not a record from the
nineteenth century.

In this case the judgment matches a real historical tie, since Gaskell knew
Brontë and wrote her biography. The link still does not measure that tie. It
exists because the biography is mentioned in the article text and Wikipedia's
style is to link the first mention of another article's subject. A connection
of equal importance that no editor happened to write about would leave no link,
and a trivial one that did get written about would leave the same link as this
one.

So the links table describes how Wikipedia's editors wrote about these authors.
The network chapter can use it to study that, but any claim about who knew,
influenced, or read whom in the 1800s needs other evidence. The absence of a
link says even less than its presence.

2. Why the page views cover the 2025 calendar year instead of the last 365 days.

Because a fixed range makes the request the same every time the code runs. The
start and end dates (20250101 and 20251231) are written into the URL, so a
rerun next month or next year asks for exactly the same data and gets the same
answer.

"The last 365 days" is a window that moves with the date on which the code is
run. Two people running the chapter a week apart would get different numbers,
and nothing in the code would tell them why. The moving window would also defeat
the cache. Each run would build a new URL, the cache would find no stored
response for it, and every author's views would be downloaded again. With the
fixed range, the cached responses match and a rerun makes no requests.

A full calendar year is also easy to state in the manifest and covers every
season once.

3. A question about Victorian novels that daily views of the Emily Brontë article cannot answer.

Many answers work here. A good one names a question about the novels or their
history, then explains why the page views can never reach it, however much data
was collected. One example:

  How widely was Wuthering Heights read when it came out in 1847?

The views start in 2025 (and the REST API's data only goes back to 2015). They
count visits to a web page about the author, so they cannot say anything about
readers of the novel in the nineteenth century.

Other good choices:

  - Whether people who visit the article have read the novel, or why they
    visited. A view records a page load and nothing about the reader.
  - Whether Wuthering Heights is a better novel than Agnes Grey. Attention is
    not a judgment of quality.
  - How critics received the novel. That lives in reviews and letters, not in
    traffic logs.

Check that your question fails because of what the data measures. "How many
people read the article on a day in 2019" also fails, but only because of our
chosen date range, so it does not answer the question.

4. What must be documented about the birth years, death years, and gender in the second corpus.

Their provenance: where the values came from and who put them there. The
reading says these fields were compiled by hand and were not returned by any
API. A reader who wants to verify them has to check them against sources other
than Wikipedia, so the documentation has to state that plainly.

At a minimum, a record of that table should say:

  - that the columns were compiled by a person, who that was, and when;
  - which sources the values were taken from;
  - how uncertain values were handled, such as authors whose birth year is
    known only approximately (Marie de France, for example), and whether such
    values were rounded, estimated, or left blank;
  - how the gender and era categories were defined and assigned.

Without this, a reader cannot tell a checked fact from a guess, and cannot tell
which columns can be rebuilt from the cache and which cannot. The API tables
can be regenerated by rerunning the code. The curated file cannot, so any error
in it passes unnoticed into the temporal analysis.

5. What it means that an unmatched title would have failed "silently," and what the corpus would have looked like unchecked.

Failing silently means the code keeps running and produces a normal-looking
result with no error or warning. When a title matches no article, the Action API
does not refuse the request. It returns a page marked "missing," and our code
turns that into a null page_id. The .drop_nulls(c.page_id) step then removes
the row. Nothing crashes and nothing is printed, and the table simply has fewer
rows than the list we started with.

In the second corpus, two titles only matched after following the server's
substitutions. "Katherine Philipps" was a typo, and "Margaret Cavendish" is a
redirect to the article's full title. Without following redirects, both authors
would have dropped out and the corpus would have had 73 authors instead of 75.
Anyone using it would have seen a clean table and had no reason to think anything
was missing.

The loss would not have been random. Both are seventeenth-century women, and
they are two of the only three women the list places in that era. Any
comparison of gender across eras would have been skewed. This is why the reading
puts the null page_id check in the code, where it runs every time, rather than
relying on memory of having checked once.
